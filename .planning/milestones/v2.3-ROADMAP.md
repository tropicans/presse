# Milestone v2.3: File Upload & MinIO Object Storage (Shipped: 2026-11-16)

**Phases:** 46-53  
**Shipped:** 2026-11-16  
**Status:** Completed  
**Goal:** Memungkinkan peserta form publik dan admin mengunggah file (gambar/PDF, maks 10 MB) yang tersimpan di object storage S3-compatible (MinIO, self-hosted di compose yang sama), dengan antrian lokal + sinkronisasi otomatis ketika storage gagal, dan akses file private melalui aplikasi.

## Phases Summary

### Phase 46: Foundation — Schema, Field Plumbing, MinIO Client & Credentials
- **Goal:** Membangun fondasi penyimpanan: enum `FILE` di PostgreSQL & TypeScript, tabel `submission_files` dan `file_upload_jobs` via migrasi SQL, klien S3 MinIO terisolasi, env configuration & validation, dan boot connectivity probe.
- **Requirements:** FILE-01, FILE-02, FILE-03, FILE-04, FILE-05
- **Success Criteria:**
  1. Migrasi database membuat tabel `submission_files` dan `file_upload_jobs` (`payload bytea`) serta nilai enum `'FILE'`.
  2. Klien storage `@aws-sdk/client-s3` mengunggah dan membaca file dari bucket MinIO private dengan pembuktian round-trip byte-identik.
  3. Probe konektivitas MinIO saat boot beroperasi non-fatal (degraded mode), mengizinkan app berjalan dalam mode antrian lokal bila storage tidak terjangkau.
  4. Variabel lingkungan MinIO terdaftar dan divalidasi tanpa kebocoran ke bundel browser klien.

### Phase 47: File Field Config, Builder, Editor & Renderer
- **Goal:** Admin dapat menambahkan dan mengonfigurasi field `File Upload` di builder form, dan field tersebut tampil konsisten pada editor, live preview, dan form publik dengan estetika monokromatis.
- **Requirements:** FILE-06, FILE-07
- **Success Criteria:**
  1. Pilihan tipe `File Upload` di `AdminFormEditor` dengan pengaturan label, wajib diisi, batas ukuran (maks 10 MB), preset format (gambar/PDF), dan jumlah file maksimum.
  2. Komponen dropzone monokromatis di live preview dan form publik (`AttendanceForm.tsx`).
  3. Konfigurasi `fileConfigs` tersimpan dan termuat tanpa kehilangan data di `settings_json`.

### Phase 48: Storage Abstraction & Postgres bytea Spool Layer
- **Goal:** Modul domain raw-SQL terpadu mengelola status file, antrian sinkronisasi, dan payload bytea spool dengan state machine yang ketat.
- **Requirements:** (Mendukung FILE-02, FILE-03)
- **Success Criteria:**
  1. `file-storage.ts` mengelola siklus hidup berkas: pencatatan upload, linking ke submission, lookup unduhan, klaim worker, dan pembersihan spool.
  2. State machine status penyimpanan: `PENDING_UPLOAD → QUEUED → SYNCED` (atau `FAILED` / `ORPHANED`).
  3. Seluruh payload biner tersimpan di PostgreSQL `bytea` tanpa dependensi volume filesystem host.

### Phase 49: Public Upload API & Client Upload Component
- **Goal:** Peserta formulir anonim dapat mengunggah file di `/f/[slug]` dengan drag-and-drop, progres, preview, pembatalan, validasi magic-byte, dan ketahanan terhadap kegagalan storage.
- **Requirements:** FILE-08, FILE-09, FILE-10, FILE-11, FILE-12
- **Success Criteria:**
  1. Komponen interaktif drag-and-drop murni (native drag events) dengan progress bar dan pratinjau thumbnail gambar/ikon PDF.
  2. `POST /api/public/files/upload` memvalidasi MIME via magic bytes (`file-type`), batas ukuran, dan batasan jumlah file.
  3. Upload tetap sukses (HTTP 200) dan tersimpan di spool Postgres bila MinIO mengalami downtime.
  4. Validasi submit server-side menolak field file wajib yang kosong atau fileId yang tidak sah.
  5. Rate-limiting berbasis IP dan pencegahan pemalsuan `X-Forwarded-For`.

### Phase 50: Sync Worker, Queue Processing, Retry & Orphan GC
- **Goal:** Sinkronisasi background worker memproses antrian file ke MinIO secara idempoten, menghapus payload bytea saat tersinkron, menangani retry bertahap, dan membersihkan berkas orphan.
- **Requirements:** FILE-13, FILE-14, FILE-15, FILE-16, FILE-25
- **Success Criteria:**
  1. Worker mengklaim job dengan `FOR UPDATE SKIP LOCKED` dan mengunggah ke MinIO dengan object key deterministik (`files/${fileId}`).
  2. Retry berulang dengan exponential backoff hingga 5 kali percobaan sebelum status terminal `FAILED`.
  3. Integrasi mulus dalam `scripts/submission-worker.mjs` menggunakan `x-worker-token` tanpa container baru.
  4. Payload `bytea` dinolkan (`payload = NULL`) begitu status mencapai `SYNCED`.
  5. File orphan (unggah tanpa submit) dibersihkan otomatis setelah masa retensi 24 jam.

### Phase 51: Private File Serving Route
- **Goal:** Admin terautentikasi dapat mengunduh seluruh file kiriman melalui rute privat aplikasi yang aman tanpa kebocoran URL storage publik.
- **Requirements:** FILE-17, FILE-18, FILE-19
- **Success Criteria:**
  1. `GET /api/files/[id]` melayani file khusus untuk sesi admin aktif (`getAdminSession()`), melakukan streaming dual-source (MinIO vs Postgres spool).
  2. Header keamanan ketat: `Content-Disposition: attachment` berstandar RFC 5987, `X-Content-Type-Options: nosniff`, dan `Cache-Control: private, no-store`.
  3. Validasi ID ketat dan pencegahan mutlak serangan path traversal (`../`).
  4. MinIO tetap berada di jaringan internal compose tanpa ekspos port publik ke host.

### Phase 52: Admin Surfaces & Export Integration
- **Goal:** Antarmuka admin menampilkan daftar lampiran pada detail submission, mendukung unggah lampiran susulan, menampilkan tautan aplikasi pada tabel, dan menghasilkan ekspor Excel yang aman dari formula injection.
- **Requirements:** FILE-20, FILE-21, FILE-22, FILE-23, FILE-24
- **Success Criteria:**
  1. Drawer lampiran di detail kiriman menampilkan daftar file, badge sinkronisasi, asal file (peserta/admin), dan tombol unduh.
  2. Admin dapat mengunggah berkas tambahan via `POST /api/admin/files/upload` tanpa mengubah jawaban peserta formulir.
  3. Tabel submissions menampilkan jawaban file sebagai link yang dapat diklik menuju rute unduh privat.
  4. Ekspor Excel (`.xlsx`) menyematkan hyperlink aplikasi dan menetralkan potensi injeksi formula (`=`, `+`, `-`, `@`).
  5. Penghapusan submission atau form melakukan cascading delete terhadap record database, payload spool, dan objek MinIO.

### Phase 53: Hardening, GC Tuning & QA
- **Goal:** Pengerasan keamanan memori terhadap OOM, pembersihan privasi EXIF metadata gambar, dan verifikasi menyeluruh seluruh alur produksi.
- **Requirements:** FILE-26, FILE-27, FILE-28, FILE-29
- **Success Criteria:**
  1. Batas payload 12MB ditegakkan di route handler dan konfigurasi Nginx untuk mencegah OOM.
  2. Metadata EXIF/GPS dibersihkan secara lossless dari berkas gambar JPEG dan PNG sebelum disimpan ke basis data.
  3. 246 unit tests passing across 28 suites di Vitest, clean ESLint, zero TypeScript errors.
  4. Docker Compose runtime container berhasil dibangun dan `/api/health` mengembalikan `status: ok`.
